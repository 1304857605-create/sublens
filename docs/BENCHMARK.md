## 1. 无锁音频通道(SPSC 环形缓冲)

**测什么**: 采集线程 → VAD 线程这条通道。单次入队出队的原子开销, 以及双线程真实搬运吞吐。

| 指标 | 数值 |
|---|---|
| 单次 push+pop | **1.9 ns** |
| 占 20ms 帧预算 | 0.0000% |
| 双线程搬运吞吐 | **64.0 Msamples/s** |
| 等效音频时长 | 4000 秒(200k 块 × 20ms) |
| 块延迟 p50 / p95 / p99 / max | 0 / 0 / 7 / 55 µs |
| 实时需求 | 0.016 Msamples/s(16kHz 单声道) |

> 结论: 通道余量约 4000 倍, 不是瓶颈。块延迟的 µs 级抖动来自消费者被调度器抢占,
> 对 20ms 一帧的音频流没有影响。

## 2. VAD / 端点检测

**测什么**: 单帧 CPU 成本 + 端点判定精度(用合成音频与脚本真值对比)。

| 指标 | 数值 |
|---|---|
| `EnergyVad::process` | mean **249 ns** / p50 200 ns / p95 300 ns |
| `UtteranceDetector::push_frame`(含 VAD 与语句缓存) | mean **458 ns** / p95 **1.0 µs** / max 19.4 µs |
| 单帧占 20ms 预算(p95) | **0.005%** |
| 1 分钟音频总 CPU 时间 | **1.37 ms** |
| 脚本句数 / 检出句数 | **6 / 6** |
| 语音时长误差 p50 / max | **0 ms / 10 ms** |
| 丢弃的过短片段 | 0 |

> 结论: 端侧 VAD 的开销可以忽略(每分钟音频 1.4ms CPU), 这就是"把端点判定放在端侧"
> 的可行性依据。端点误差 ≤10ms(脚本 20ms 帧粒度下已经到极限)。

## 3. 稳定前缀对齐(LocalAgreement-n)

**测什么**: confirmations 的取舍(稳定性 vs 提交延迟), 以及算法本身的 CPU 成本。

| confirmations | 提交片段数 | 平均每句片段 | 平均尾部字数 | 提交内容完整性 |
|---|---|---|---|---|
| 1 | 57 | 9.50 | 0.0 | ✓ 与原文逐字一致 |
| 2 | 50 | 8.33 | 3.6 | ✓ 与原文逐字一致 |
| 3 | 44 | 7.33 | 6.6 | ✓ 与原文逐字一致 |

| 指标 | 数值 |
|---|---|
| 单次 `on_partial` | **93.9 ns** |
| 每秒可处理 partial 数 | 1064 万 |

> 解读: confirmations 越大, 每次提交越"晚"(平均尾部多攒 3.6/6.6 字), 但换来
> 更少的错误提交; 三种取值下最终提交内容都与原文逐字一致(说明算法不会丢字)。
> 默认选 2: 尾部只多攒 3.6 字(几百毫秒的识别时间), 但能挡住单次识别纠错。

## 5. 端到端延迟 ★

**测什么**: 语音结束(端点判定) → 第一段译文出现在 HUD 的时间差, **每句只记一次**。
实时节奏下测量, 合成音频 + 模拟流式 ASR(首字 260ms), 4 句对话 × 3 种配置。

| 场景 | 端到端 p50 | p95 | p99 | 首 partial p50 | MT 往返 p50 | 提交片段 | HUD 整行替换 | 结论 |
|---|---|---|---|---|---|---|---|---|
| A 本地 MT + 草稿行 | **404** | **497** | 497 | 279 | 0 | 20 | 18 | 达标 |
| B 云端 MT(注入 180±80ms) + 草稿行 | **761** | **778** | 778 | 293 | 1150 | 29 | 0 | 超标 |
| C 本地 MT + 关闭草稿行 | **405** | **503** | 503 | 282 | 0 | 20 | 0 | 达标 |

> 口径提醒:
> - 端到端只统计"第一次上屏", 否则同一句的后续片段会让延迟虚高(一句话说 3 秒, 最后一段必然晚 3 秒);
> - 320ms 端点 hangover 计入其中(它是"说完到判定说完"的真实延迟);
> - 云端 MT 的 180±80ms 是**注入模型**, 且注入器是**单连接串行**模型(一次只有一个在飞请求),
>   所以 MT 往返里包含了排队(1150ms); 真实云服务可以并发, 这里故意取保守值;
> - B 超标是真实结论而不是 bug: **云端 MT 会吃掉 700ms 预算里的大头**。要达标只能
>   把 MT 放端侧, 或把 hangover 从 320ms 降到 240ms 再加并发连接。这条取舍写进了
>   [LATENCY-BUDGET.md](LATENCY-BUDGET.md) 的"优化手段与代价"。

## 6. 引擎吞吐(注入时延置 0, 全速跑)

**测什么**: 去掉网络与模型时延后, 引擎自己能把音频跑多快 —— 直接对应眼镜端 CPU 余量。

| 指标 | 数值 |
|---|---|
| 音频总时长 | **89.6 秒**(36 句) |
| 墙钟耗时 | **1.632 秒** |
| 实时倍率 | **54.9x** |
| 单核 CPU 占用(估算) | **1.82%** |
| 检出句数 | **36 / 36** |
| 提交翻译片段 | 216 |
| 音频丢帧(样本) | **0** |
| VAD 单帧 p95 | **2 µs** |

> 结论: 实时倍率越高, 端侧留给显示/传感器/网络的 CPU 余量越大。

## 8. 这些数字不能证明什么(边界)

1. **ASR 与 MT 不是真模型**: 识别率、翻译质量、真实网络时延都不在这份报告里;
2. **没有真机数据**: 功耗、发热、波导显示的实际可读性需要眼镜真机;
3. **单机单次**: 没有做多轮统计与方差分析, 延迟数字应视为"量级正确, 个位数不可信";
4. **内存/包体未测**: 端侧模型接入后需要重新评估。
