# 延迟预算(Latency Budget)

> 这份文档回答两个问题: **700ms 是怎么拆出来的**, 以及**每一段怎么验证**。
> 所有数字都有测量口径; "实测"一列来自 `sublens_bench` 与 `sublens_demo`, 可在本机复现。

---

## 1. 口径定义

**端到端延迟 = 说话人闭嘴的那一刻 → 译文出现在眼镜上的那一刻**

```text
说话人闭嘴
   │ ①端点判定 hangover
   ▼
判定说完, 整句送 ASR
   │ ②首字延迟 (网络 + 云端解码)
   ▼
第一个 partial 回来
   │ ③稳定前缀对齐 (要等确认, 通常已经包含在 partial 里)
   ▼
稳定片段送翻译
   │ ④MT 往返
   ▼
译文到达调度器
   │ ⑤HUD 帧(≤1/fps)
   ▼
用户眼睛看到
```

为什么不用"说话开始"算: 那会把句子本身的长短算进延迟, 失去可比性。
产品上真正影响体验的是"他说完多久我能看到这句话的意思"。

---

## 2. 预算拆解

| 阶段 | 预算 | 来源 / 可调性 |
|---|---|---|
| ① 端点判定 | **320ms** | `UtteranceDetector::hangover_ms`, 240~400 可调; 越小响应越快, 但句中停顿会被切断 |
| ② ASR 首字延迟 | **260ms** | 云厂商决定; 端侧模型可到 100~200ms, 但精度下降 |
| ③ 稳定前缀对齐 | **≈0ms** | 纯 CPU 算法, 实测亚微秒级; 但"等确认"会带来 0~1 个 partial 的等待(通常已在 ② 内) |
| ④ MT 往返 | **本地 1~5ms / 云 180±80ms** | 部署方式决定 |
| ⑤ HUD 上屏 | **≤50ms** | 20fps 帧间隔; 单帧渲染成本实测 <1ms |
| **合计** | **本地 ≈580ms / 云 ≈760ms** | |

> 结论: p95 要压到 700ms 以内, **要么 MT 放本地, 要么把端点 hangover 降到 240ms**。
> 这两条就是"超低延迟"真正的工程抓手, 而不是换个更快的模型。

---

## 3. 各段怎么测

| 段 | 测量方法 | 代码位置 |
|---|---|---|
| 端点 | 合成音频 + 脚本真值, 比较 `speech_duration_ms` 与脚本时长 | `bench/bench_vad.cpp` |
| ASR 首字 | `speech_end_to_first_partial` 直方图 | `src/app/pipeline.cpp` |
| 对齐算法 | 200 万次 partial 迭代的 ns/次 | `bench/bench_stabilizer.cpp` |
| MT 往返 | `mt_roundtrip` 直方图(模拟器可注入) | `src/app/pipeline.cpp` |
| HUD | `render_to_string` 单帧耗时 | `bench/bench_hud.cpp` |
| **端到端** | `speech_end_to_hud`: 每句**第一次**译文上屏的时延 | `src/app/pipeline.cpp` |

## 4. 优化手段与其代价

| 手段 | 收益 | 代价 |
|---|---|---|
| hangover 320→240ms | -80ms | 句中停顿 >240ms 就会被切成两句, 译文语境变碎 |
| ASR 换端侧小模型 | -100~160ms | 识别率下降, 口音/噪声场景更明显 |
| MT 放本地 | -180ms | 质量下降(端侧小模型), 内存/功耗上升 |
| 草稿行(推测翻译) | 用户更早看到**内容**(约 -200ms 体感) | HUD 整行替换次数上升, 翻译请求数增加 |
| 稳定前缀 confirmations=1 | 更早上屏 | 识别纠错时字幕会回退, 违反"只增不改" |
| HUD 帧率 20→30fps | -17ms | 功耗上升, 波导屏收益有限 |

本项目的默认组合是: **hangover 320 + 云 ASR 260 + 本地 MT + 20fps + 草稿行开**
= p95 在 700ms 预算内, 且字幕稳定。

## 5. 实测结果

> 见 [BENCHMARK.md](BENCHMARK.md) 的"端到端延迟"与"VAD/端点"两节(本机实测)。
> 摘要(实时节奏、合成音频、模拟 ASR 首字 260ms、本地 MT):

| 场景 | p50 | p95 | 结论 |
|---|---|---|---|
| **本地 MT + 草稿行(默认)** | **404ms** | **497ms** | 达标(预算 700ms, 余量约 200ms) |
| 云端 MT(注入 180±80ms) | 761ms | 778ms | **超标** —— MT 一去云端就吃掉预算 |
| 本地 MT + 关闭草稿行 | 405ms | 503ms | 延迟基本不变, 草稿整行替换 0 次 |

> 结论很明确: **700ms 预算的分水岭是 MT 放端侧还是云端。** 端侧 MT 时 p95≈500ms,
> 还有 200ms 余量可以给网络抖动; 换成云端 MT 直接 780ms 超标。
> 如果产品必须用云端 MT, 就必须把 hangover 降到 240ms(-80ms) 并保证并发连接, 才能压回预算内。

> ⚠️ 边界: ASR/MT 的时延是**参数化注入**, 不是真实云服务实测。
> 接真实服务后需要重跑 `sublens_bench latency` 把注入值换成实测值。

## 6. 如果要在真机上守住这个预算

1. **音频链路**: AAudio 低延迟模式 + 20ms 帧, 不要用 Java AudioRecord 的默认缓冲(可能有 100ms+);
2. **线程优先级**: 采集与 VAD 线程提到 `THREAD_PRIORITY_URGENT_AUDIO`, 避免被 UI 线程抢占;
3. **网络**: 云端连接常驻(不要每句重连), 开 TCP_NODELAY, 弱网时降级到端侧模型;
4. **渲染**: HUD 与业务解耦, 20fps 固定节拍, 不要在渲染线程里做字符串格式化(预计算);
5. **监控**: `speech_end_to_hud` 的 p95 必须打进日志/上报, 否则延迟劣化没人发现。
