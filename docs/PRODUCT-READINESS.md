# 这能不能成为"真正的实时翻译"?

> 这是对项目的**自我审计**, 不是宣传材料。判断标准只有一个:
> **陌生人戴上它, 在真实对话里连续用 10 分钟, 会不会想摘下来。**
> 能 → 是产品; 不能 → 是赛博文具。

---

## 1. 结论先说

现在的形态是 **"真引擎 + 假模型"**:

| 层 | 状态 |
|---|---|
| 延迟架构(分段预算、端点、稳定前缀、双行 HUD、句末校正) | **真的**, 有实测和单测 |
| 可替换后端(ASR/MT/音频/显示四个接口) | **真的**, 换模型不用改流水线 |
| 证据链(67 个单测 + 6 组基准 + 口径文档) | **真的**, 一条命令可复现 |
| 语音识别 / 翻译质量 | **假的**(脚本模拟 + 模板短语表) |
| 麦克风 / 眼镜显示 / 网络 | **假的**(合成音频、终端 ANSI、无网络层) |
| 真机功耗 / 发热 / 佩戴体验 | **完全没测** |

所以答案是: **它有成为真产品的地基, 但现在还不是产品。** 差的是三件事:
**真模型、真机、真对话场景**。前两件是工程(2~4 周), 第三件是产品(4~6 周)。

---

## 2. "实时翻译"的物理下限是多少

翻译必须等一句话说完才能准确(否则就是瞎猜), 所以延迟 = 端点 + 识别 + 翻译 + 显示:

| 环节 | 激进值 | 常规值 | 说明 |
|---|---|---|---|
| 端点判定(hangover) | 240ms | 400~600ms | 商用产品普遍偏保守, 怕切碎 |
| ASR 首字 | 200ms | 300~500ms | 云端流式; 端侧小模型 150~400ms |
| 翻译 | 80ms | 150~300ms | 云端; 端侧小模型 20~80ms |
| 上屏 | 30ms | 50ms | 帧率决定 |
| **合计** | **≈550ms** | **≈900~1400ms** | |

我们本机测到的 **p95 497ms** 是在"本地模板 MT(≈0ms)"前提下, 已经贴到物理下限附近。
**接上真实云端 MT 后, 现实预期是 700~900ms** —— 这才是拿去和甲方说的数字。
497ms 的用途是证明"引擎本身不吃延迟", 不是产品指标。

> 参照系: 市面上手机实时字幕/翻译 App 普遍 1~2 秒, 专业同传设备 2~5 秒。
> 所以 800ms 左右"说完就看到"已经是**第一梯队**的体验。

## 3. 差距清单(按投入产出排序)

| # | 缺什么 | 现在 | 目标 | 工作量 | 风险 |
|---|---|---|---|---|---|
| 1 | 真 ASR + 真 MT | 模拟器 / 模板 | 接 1 家云(如阿里/讯飞/OpenAI)+ 1 家 MT | **3~5 天** | 低:接口已留好 |
| 2 | 真人音频素材 | 合成音 | 自己录 30 分钟中英对话(不同口音/噪声) | 1 天 | 低 |
| 3 | 真实延迟复测 | 注入模型 | 用真 API 重跑 `bench.cmd`, 把 BENCHMARK 的"注入"改成"实测" | 1 天 | 低 |
| 4 | 真麦克风采集 | 合成音源 | AAudio(Oboe), 16kHz/20ms 低延迟 | **3~5 天** | 中:设备差异 |
| 5 | 眼镜显示 | 终端 ANSI | GLES 或厂商 HUD SDK | 3~5 天 | 中:安全区/亮度 |
| 6 | **双人对话** | 单人独白 | 说话人分离/双麦波束, 知道"谁在说" | **2~4 周** | **高:最大坑** |
| 7 | 噪声鲁棒性 | 安静环境 | 60dB 咖啡厅可用 | 1~2 周 | 中:靠模型 |
| 8 | 功耗/热/连续运行 | 未测 | 眼镜端增量 < 1.5W, 30 分钟不降频 | 1~2 周 | 中:要真机 |
| 9 | 隐私合规 | 无 | 录音指示 + 本地模式 + 条款 | 3 天 | 低:必做 |

**第 6 项是最容易被忽略、也最致命的一项**: 眼镜只有一副麦克风时, 两个人说话是混在一起的。
没有说话人分离, 字幕就会"A 说一半, B 的话插进来", 那是无法阅读的。
商用同传设备靠指向性麦克风阵列或双设备协同解决, 这是"演示能跑"和"真能用"的分水岭。

## 4. 三个里程碑(每个都有可量化的验收)

### M1 "接上真服务"(2 周)

做什么: 接云 ASR + 云 MT, 用真人录音跑通全链路; 把 BENCHMARK 里的注入数字换成实测。

**验收(硬指标)**:
- [ ] 真实云端链路下 p95 ≤ 900ms(说完→上屏)
- [ ] 50 句真人对话的字幕可读率 ≥ 90%(自己逐句读, 记录"能看懂"的比例)
- [ ] 真实云 API 报错/超时时有明确降级提示, 不静默卡死

### M2 "上真机"(3~4 周)

做什么: AAudio 采集 + GLES 显示, 在一台 Android 眼镜上连续跑。

**验收**:
- [ ] 眼镜上连续 30 分钟: 不崩、内存波动 < 10%
- [ ] 端到端延迟比桌面端劣化 ≤ 150ms(端侧采集+显示的开销)
- [ ] 录一段 3 分钟真机视频(这是接单时最有说服力的物料)

### M3 "真场景可用"(4~6 周)

做什么: 双人对话(说话人分离)、噪声环境、断网降级、佩戴舒适度。

**验收**:
- [ ] 5 个陌生人各用 10 分钟: 满意度 ≥ 4/5, 愿意再用
- [ ] 60dB 噪声环境可读率 ≥ 75%
- [ ] 双人对话时"谁在说"归属正确率 ≥ 85%

> M1 完成 = **可交付的工程能力**(客栈接单用这个即可);
> M2 完成 = **有真机作品**(报价能上一个档);
> M3 完成 = **能卖给终端用户的产品**。

## 5. 什么时候它会被判定为"赛博文具"(红旗清单)

出现任意一条, 就是文具:

- [ ] 只在 demo 脚本上有效: 换一段真实录音就崩;
- [ ] 延迟数字只有"注入模型", 从没接过真 API;
- [ ] 只能单人独白, 双人对话字幕就乱;
- [ ] 没有真机, 只有终端截图;
- [ ] 翻译质量没法评价(没有人工可读率记录);
- [ ] 只敢演 30 秒, 不敢连续跑 30 分钟;
- [ ] 一被问"噪声环境怎么样"就答不上来。

**避免方法**: 每一项都留证据 —— 录音文件、复测表格、真机视频、可读率统计、连续运行日志。
这也是客栈作品集和面试时唯一有效的东西:**证据, 而不是功能列表**。

## 6. 商业上怎么定位(直接决定你怎么接单)

| 定位 | 卖什么 | 客户 | 议价能力 |
|---|---|---|---|
| **A. 端侧实时字幕引擎(中间件)** | 一套可集成的 C++ 引擎 + 适配层 + 基准报告 | 做眼镜/耳机的硬件公司 | **高**:他们缺的是这块能力, 不是又一个 App |
| B. 定制 Demo | 按客户场景做一个能演示的原型 | 想验证方向的产品团队 | 中 |
| C. 消费级翻译 App | 完整产品(账号/订阅/客服) | 终端用户 | 低:获客成本高, 单人做不了 |

**建议走 A**: 你已经把"引擎 + 接口 + 基准 + 文档"做出来了, 这是硬件公司最愿意买的东西;
他们最怕的是"外包做了一个 demo, 结果没法集成进自家设备"。

对客栈单子的直接含义:
- M1 没做完时, 接"技术方案 + Demo"类小单(5k~3w);
- M1 做完后, 可以接"端侧引擎接入"类单(3w~6w);
- M2 做完(有真机视频)后, 报价可以再上浮 30%~50%。

---

## 7. 一句话总结

> **架构是真的, 模型是假的。** 把模型换成真的、把设备换成真的、把场景换成真人的,
> 它就是产品; 停在 demo 和截图里, 它就是文具。
> 而这两者之间的距离, 不是"再写 5000 行代码", 而是 **M1/M2/M3 三个里程碑的验收清单**。
